# B1 — расследование: isext, grid, рубрики, источники тела

Дата: 2026-08-24. Только чтение, ничего в данных и коде не менялось.
Задача — проверить две ошибки декомпозиции (`pg_txt`, корпус 1523) и выяснить,
не питается ли журнальная статья содержимым из мест, кроме `articlex.body`.

## Источник и метод

- Данные — дамп `DB/2018-11-17_02-10_db_idrp.sql` (16 ГБ, mysqldump, MySQL 5.7).
  Живого доступа по SSH в конвейере нет: скрипты `scripts/` работают по дампу,
  а `.env.local` с `SSH_*`/`LEGACY_DB_*` лежит в `../journal` (приложение).
  Заявленный в задаче путь `scripts/migration/` — фактически `scripts/`.
- Секции таблиц вырезаны по байтовым смещениям (рецепт из шапки
  `legacy_dump_parser.py`): `articlex` 160794099..200486879 (~39.7 МБ),
  `dic`+`dic_data` 2538197880..2538348760.
- «Запросы» прогнаны разовым скриптом на извлечённых секциях, импортирующим
  `parse_rows` из проектного парсера (проектные файлы не трогались).
- Код рендера: `../legacy/article.php` (рендер articlex), бин
  `../legacy/_src/bean/articlex.php`.

## Две ошибки декомпозиции — подтверждены обе

- **`pg_txt`** — изобретённое имя (см. п.1).
- **1523** — это корпус *до* вывода именинного куста в арку C:
  1345 + типы 14 (51) + 15 (38) + 18 (89) = 1523. Контрольный прогон даёт
  корпус ровно **1345**, посумма по типам совпала с `legacy-data-facts.md`:
  `{1:32, 2:8, 3:18, 4:1199, 5:18, 6:1, 17:66, 20:2, 26:1}` (всего строк 1662,
  колонок 50).

## 1. Существует ли имя `pg_txt`

Проверено: DDL `CREATE TABLE articlex` из дампа; `grep pg_txt` по `../legacy`,
по `journal-docs` и `journal-ai`.

Вывод: `pg_txt` не существует нигде в реальности. Тело статьи — колонка
**`body` mediumtext COMMENT 'Текст статьи'**; префикс `pg_` несут только три
SEO-поля (`pg_ttl`/`pg_dsc`/`pg_kwd`). В легаси-коде 0 вхождений. Имя `pg_txt`
встречается **только в наших документах** — в самой декомпозиции
`ark-b/b1-decomposition.md:78,115` (стадии S4-S5) и в заметках об этой же
ошибке (`DEBT-B.md:35`, `DEBT-B-v2.md:37`, `legacy-data-facts.md:12`).
Версия «изобретено по аналогии с pg_ttl/pg_dsc/pg_kwd» — верна.

## 2. `isext` (DDL: «Признак того, что статья хранится не здесь»)

Проверено: запрос `isext=1` по секции; `grep isext ../legacy`; `article.php`;
бин `articlex.php`; наличие файлов на диске.

Вывод: ровно **4 строки** `isext=1`, все **type=1 и все в корпусе**, у всех
**`body` пустое (0 байт)**, `url` держит внешний абсолютный адрес:

| id | url (в поле url) | файл на диске | размер |
|----|------|------|------|
| 4 | …/htm/fair/html/ignatii-bryanchaninov.htm | есть | 9 160 б |
| 5 | …/htm/fair/html/feofan-zatvor.htm | есть | 19 100 б |
| 6 | …/htm/fair/ioann-zlatoust.htm | есть | 27 631 б |
| 60 | …/htm/fair/nilus.htm | есть | 17 615 б |

Рендер `isext` **не обрабатывает вообще**: `article.php:59` берёт
`$body = trim($article["body"])`, бин `articlex::getOneX` (`articlex.php:7`) —
голый `SELECT * FROM articlex WHERE id=?` без ветки на isext. Единственное
упоминание `isext` во всём легаси — `buy/mv_lvl.php:26` (`WHERE isext<>1`),
и то лишь чтобы исключить их из индекса товарных рекомендаций.
**Тело этих 4 статей — в статических htm-файлах на диске** (раздел «ярмарки»
`htm/fair/…`), на которые указывает `url`; в БД его нет.

## 3. Пустое `body` в корпусе

Проверено: условие `len(trim(body)) < 100` по корпусным типам (NULL = длина 0).

Вывод: `MIN(LENGTH(body)) = 0`; строк < 100 байт — **7**:

| id | type | len | pg_ttl |
|----|----|----|----|
| 4, 5, 6, 60 | 1 | 0 | те самые isext, тело в htm-файлах |
| 1022 | 17 | 0 | «Предисловие \| Добротолюбие избранное для мирян» |
| 1045 | 1 | 0 | «Поздравление с именинами Германа…» |
| 1626 | 26 | 47 | «Молитвы, православные молитвы…» (тело контейнера под grid, см. п.6) |

Помимо 4 isext есть 3 «настоящих» пустых: 1022 и 1045 — без тела,
1626 — контейнер под grid-вставку.

## 4. Расхождение по пустым слагам

Проверено: `url==''` и `url IS NULL` с разбивкой по type; отдельно по корпусу.

Вывод: оба числа верны, но считают разный охват. По ВСЕЙ таблице `url==''` —
**22** (NULL — 0), по типам: **19→8, 8→6, 25→5, 4→2, 0→1**. По корпусу
(1,2,3,4,5,6,17,20,26) пустых слагов — **2**: id **1226** и **1545**, оба
type=4 (как в `legacy-data-facts.md`). Разница в 20 — только некорпусные типы
(Фрагменты 19, Служебные 8, Рубрикатор 25, тип 0). `legacy-map.md` («22»)
мерил всю таблицу, факты («2») — корпус; противоречия нет.

## 5. Рубрика для фронтматтера (dic_data 17/20), сироты FK

Проверено: секция `dic_data`, карты up=17 и up=20; сверка корпуса.
Каноничный join — как в бине `articlex.php:42`
(`LEFT JOIN (select * from dic_data where up=20) d20 ON d20.n = a.src_saints`).

Запрос «id → человекочитаемая рубрика»:

```sql
SELECT a.id,
       d17.name AS rubrika,        -- тип статьи, dic 17
       d20.name AS razdel_zhitiy   -- раздел ЖС, dic 20 (для type=4)
  FROM articlex a
  LEFT JOIN dic_data d17 ON d17.up = 17 AND d17.n = a.type
  LEFT JOIN dic_data d20 ON d20.up = 20 AND d20.n = a.src_saints
 WHERE a.type IN (1,2,3,4,5,6,17,20,26);
```

Сирот нет: `dic17` — 27 значений, `dic20` — 5; в корпусе **0** статей с
нерезолвящимся `type` и **0** с нерезолвящимся `src_saints`. Раскладка
`src_saints` по корпусу `{0:149, 1:5, 2:41, 3:1148, 4:2}` — все значения
(включая 0 = «без источника») присутствуют в `dic20`.

## 6. `grid_tp` / `grid_art_*` (встраивание чужих статей)

Проверено: `grid_tp != 0` по секции; механика в `article.php:74-104` и
`article.php:422-430`.

Вывод: непустую композицию имеют **2 корпусные статьи** (и всего 2 в таблице):

| id | type | grid_tp | что подставляется |
|----|----|----|----|
| 1003 | 17 (Добротолюбие) | 1 | слот **left** → тело статьи **id 1230** (ширина 450) |
| 1626 | 26 (Молитва) | 1 | слот **left** → тело статьи **id 1627** (ширина 200) |

При `grid_tp≠0` рендер тянет `articlex::getOne` по
`grid_art_left/right/top/bottom` и кладёт их **`body`** в шаблон рамкой вокруг
основного тела. Обе цели — **id 1230 и 1627 — это type=19 «Фрагменты страниц»
(вне корпуса)**, рекламные вставки. То есть на 2 корпусные страницы помимо
`body` подставляется тело чужой, некорпусной строки.

## 7. Другие источники содержимого корпусной статьи

Проверено: DDL всех колонок; `anons`; трасса `article.php` целиком; бин целиком.

Кроме `articlex.body` своей строки, в страницу попадают:

- **статические htm-файлы на диске** — реальные тела 4 статей `isext=1`
  (`htm/fair/…`), в БД тела нет (п.2). Единственное «другое место», где лежит
  проза корпуса.
- **тела других строк `articlex`**: общий подвал — `body` строки **id 572**
  (type 8 «ФУТЕР.», 356 б) цепляется почти ко всем статьям
  (`article.php:373-381`); grid-вставки id 1230/1627 (type 19) на 2 страницах.
- **динамически генерируемое** (не хранимый контент): «Сегодня память св.»
  для type 4/7/22 (`getTodaySaintsHTML`, из `src_saints=3`+`cal`+дата), списки
  детей раздела (`block_list`/`block_last`), таблицы именин, месячные указатели,
  alt-saints — всё это `hrefs` на лету; правый столбец — товары магазина
  (`DoRightShopWindow`), не журнал.
- **колонка `anons` (text)** — второй кандидат в HTML — **пуста во всей
  таблице** (0 непустых, max len 0); рендер её не читает.

Других источников нет: по схеме единственная content-несущая колонка — `body`
(`anons` пуст), по обеим точкам рендера (`article.php`, бин) подхвата файлов
по id/имени, кроме htm-файлов isext, и отдельных контентных таблиц не найдено.

## Осталось предположением

- **Как isext-статьи отдавались вживую.** Файлы на диске есть, тело в БД пусто,
  `article.php` вернул бы пустоту. Каким маршрутом live-сайт показывал контент
  (прямой линк на `htm/fair/*.htm`, редирект, иначе) — по коду не видно;
  `.htaccess` не трассировал.
- **Резолвинг `pers_saints`→dic22.** Проверял только `type`→17 и
  `src_saints`→20. Словарь dic22 (~1184 значения) не выгружал; сироты «о ком
  житие» не считал.
- **Свежесть дампа.** Всё по дампу 2018-11-17; код правился до 2024. На проде
  строк, вероятно, чуть больше (AUTO_INCREMENT=1666); числа корпуса финально
  сверять на свежем дампе.
- **`grid_tp` кроме 1.** Оба случая — `grid_tp=1` и только слот `left`; другие
  раскладки (top/bottom/right) в данных не встретились.
- **Строки 572/1230/1627 при отборе 1345.** Некорпусные (type 8/19), питающие
  корпусные страницы. Попадут ли в перенос и что делать с подвалом/рекламой —
  решение владельца, здесь только зафиксирована зависимость.
