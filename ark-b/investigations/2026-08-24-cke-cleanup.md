# Чистка мусора CKEditor из тел `articlex` — холостой прогон (фаза 1)

Разовая правка данных в легаси-базе по решению владельца от **2026-08-24**:
вычистить служебный мусор редактора CKEditor из колонки `body`. Редактор на
сайте больше не используется — новый мусор появляться некому. Это единственное
санкционированное исключение из правила «базу не правим»; всё прочее — только
чтение.

Операция двухфазная. **Фаза 1 (этот документ) — только чтение**, ничего в базе
не изменено. Фаза 2 (запись) выполняется только после явного «да» владельца и
получения отдельных UPDATE-реквизитов.

Источник: та же легаси-БД (дамп 2018-11-17, MySQL 5.7), что и в
`legacy-data-facts-v2.md`. Тела в cp1251-таблице, сервер сам перекодирует
cp1251 → utf8 соединения; в программе — обычные строки JS.

## Метод (read-only)

- Скрипт `scripts/migration/clean-cke.ts`, команда `dry-run` (`npm run cke:dry-run`).
  Один `SELECT id, type, LENGTH(body), CHAR_LENGTH(body), body FROM articlex`
  по **всей** таблице — чистим базу, а не выборку корпуса. `corpus.jsonl`
  покрывает лишь 1345 корпусных строк; 317 некорпусных прошли только здесь.
- Признак заражения — два именованных сигнала: литеральный `<style` **или**
  `{cke_protected}` в теле.
- Очищенные тела строятся той же функцией `cleanBody`, что пойдёт в фазе 2.

## Что найдено

Заражённых — **13**. Известная владельцу десятка (23, 24, 25, 27, 47, 49, 50,
51, 53, 59) подтверждена полностью; сверх неё скан всей таблицы вскрыл **три

## Устройство мусора (два абзаца)

Мусор — это HTML-элементы `<style>…</style>`, осевшие внутри тела статьи. У
десяти строк это protected-source механизм CKEditor: при вставке из
LibreOffice/OpenOffice редактор заворачивал чужой CSS в комментарий
`<!--{cke_protected}{C}<CSS в percent-энкодинге>-->` внутри `<style>`. Пример
одиночного прохода — id 25: заэкранированный блок `@page { size: 21cm 29.7cm;
margin: 2cm } P { margin-bottom: 0.21cm }`. У трёх других строк (26, 1624, 1640)
`{cke_protected}` нет вовсе — там просто вставленные в тело таблицы стилей
(кнопка `a.btn { … }` у 26; навигация `ul/li/a.blue { … }` у 1624 и 1640). И то,
и другое браузером как текст не рендерится (`<style>` — raw-text-элемент), поэтому
видимый читателю текст от их удаления не меняется.

Почему id 23 раздулся до **771 КБ**: 39 блоков `<style>` дают 713 827 Б — **92.6 %**
тела. Дело не в объёме контента, а в **рекурсивном перекодировании**. Каждое
повторное сохранение статьи в CKEditor заново «защищало» уже защищённый блок,
накладывая ещё один слой percent-энкодинга поверх предыдущего:
`<` → `%3C` → `%253C` → `%25253C` → `%2525253C` …, и `{cke_protected}` →
`%7Bcke_protected%7D` → `%257Bcke_protected%257D` → … Percent-энкодинг примерно
утраивает каждый спецсимвол за проход, так что за десяток циклов правок пара
тривиальных CSS-комментариев разрослась геометрически. Явно видно в id 47
(один блок — 26 937 Б, сплошной каскад `%25…`). То есть 771 КБ id 23 — это не
данные, а многократно переэкранированная пустота.

## Граница чистки

**Вырезается** (единственная операция правки, функция `cleanBody`):

1. Весь элемент `<style …>…</style>` целиком (нежадно, до первого `</style>`).
2. Защитно — protected-комментарий вида `<!--{cke_protected}…-->`, если бы он
   встретился вне `<style>` (в этих 13 строках все `{cke_protected}` лежат
   внутри `<style>`, поэтому п. 2 фактически ничего не добавляет; оставлен как
   страховка на переимпорт).

**Остаётся нетронутым** всё прочее: инлайн-атрибуты `style="…"`, `<font>`,
`<span>`, `<p>`, HTML-сущности (`&nbsp; &mdash; &#1123;` …), изображения,
таблицы, текст. Формально это либо контент, либо форматирование, не совпадающее
с сигнатурой мусора.

**Отсеянные кандидаты** (похоже, но НЕ трогаем): id 19 — `<!--pagebreak-->` и
`<!--|-->` (CMS-маркер разбивки на страницы и служебный разделитель, а не мусор
CKEditor); id 67 — `<o:p></o:p>` (Word-namespace от вставки из Word). Оба сигнала
`<o:…>`/`mso-` в известной десятке не встречаются ни разу, поэтому по условию
задачи («следы, вскрывающиеся при разборе известных десяти») они вне границы.
Это отдельные истории, если до них дойдут руки.

## Три свойства чистки и как они проверены

- **P1 — видимый читателю текст до и после совпадает.** Сравнивается не сырой
  HTML, а «видимый текст»: из тела удаляются `<script>`, `<style>` и
  HTML-комментарии (браузер их как текст не рисует), затем снимаются все теги,
  декодируются HTML-сущности в глифы, и пробелы нормализуются (любая серия
  пробельных символов → один пробел, обрезка по краям — как схлопывание
  whitespace в HTML). Полученные строки «до» и «после» сравниваются побайтно.
  Результат: **13 из 13 без расхождений**.
- **P2 — чистка незаражённого тела не меняет ни байта.** `cleanBody` прогнана по
  **всем 1649 незаражённым** строкам таблицы: изменённых — **0**.
- **P3 — повторная чистка уже очищенного не меняет ни байта.** Для каждой из 13
  строк `cleanBody(cleanBody(x)) === cleanBody(x)`: нестабильных — **0**;
  остаточных маркеров (`<style` / `</style` / `{cke_protected}`) в очищенных —
  **0 строк**.

Байтовая вменяемость: NULL-тел 0; строк, где JS-длина ≠ `CHAR_LENGTH`, — 0;
строк, где `LENGTH(байты)` ≠ `CHAR_LENGTH`, — 0.

## Фаза 2 — применение (ВЫПОЛНЕНО 2026-08-25)

Владелец дал явное «да» 2026-08-25. UPDATE-реквизиты выданы отдельным пользователем
(штатный пользователь конвейера — только SELECT) и после операции отзываются.
Команда `apply` (`npm run cke:apply`) под защёлками (`CKE_APPLY_CONFIRM` +
`LEGACY_DB_WRITE_*`), из терминала владельца. Транзакция COMMIT выполнена успешно;
машинный итог — `journal/var/cke/phase2-result.json`.

**Бэкап (шаг перед записью).** Драйверный (mysqldump-CLI в окружении нет, база —
только через SSH-туннель): снимок `body` всех строк в
`journal/var/cke/backup/articlex-body-2026-08-25-10-20-26.sql` — **38 840 839 Б,
1662 обратимых `UPDATE`**. Снят ДО правки, хранит исходные тела (строка id 23 —
792 034 Б, содержит `{cke_protected}` и `<style>`). Восстановление — прогнать файл
через то же соединение (utf8→cp1251, как при чтении). Гейт пройден: файл ненулевой,
строк ровно 1662, иначе запись бы не началась.

**Правка.** Одна транзакция, `UPDATE articlex SET body=? WHERE id=?` только для 13
заражённых id (23, 24, 25, 26, 27, 47, 49, 50, 51, 53, 59, 1624, 1640), только
колонка `body`, та же cp1251-кодировка соединения. Каждая правка `affectedRows=1`.
Освобождено **1 133 993** символа (== cp1251-байта).

**Пост-проверки** (свежее чтение после COMMIT):

| Проверка | Результат |
|---|---|
| Маркеры `<style` / `{cke_protected}` по всей таблице | **0** ✓ |
| Каждая правленая строка перечитана, побайтно == «после» фазы 1 | **13 / 13** ✓ |
| Строк в таблице | **1662** ✓ |
| 5 контрольных незаражённых (id 3, 4, 5, 6, 7) побайтно без изменений | **5 / 5** ✓ |

(Те же проверки + `affectedRows==1` и число строк 1662 прогнаны и ВНУТРИ транзакции
до COMMIT — при любом несовпадении был бы ROLLBACK без единой правки.)

**Напоминание владельцу:** отозвать право UPDATE у использованного пользователя и
удалить строки `LEGACY_DB_WRITE_*` из `.env.local`.

Ничего не закоммичено — отчёт, скрипт и пары «до/после» остаются на ревью.
