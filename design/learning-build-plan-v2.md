# Учебно-строительный план — вертикаль журнала

> Кому: владелец (пишет код сам, учит TS/React/Next.js) + Claude (чат — разбор
> концепций и ревью; Claude Code — наставник-ревьюер в learning-режиме, не автор).
> Где живёт: `journal-docs/design/`. Как пользоваться: один шаг = один заход
> (и обычно один новый чат). Не начинать следующий шаг, пока не выполнен критерий
> «Готово» текущего.
>
> **Ревизия 2026-07-22** (по итогам прохода A0–A8): добавлены статусы шагов,
> арка A′ «Статья и главная по дизайну», скорректированы B2/B6, добавлена
> арка C «Именины». Принятые решения ревизии: (1) MockProductSource и полка
> поднимаются из B6 в A10–A11 — статья верстается «полностью по дизайну» с
> живой полкой на фикстурах; (2) главная строится ДО B2 на фикстурах, реальные
> данные подключаются в B2; (3) именины — отдельная арка C после B5.

## Правила режима обучения

1. **Пишу сам всё, что учит:** компоненты, типы, Zod-схемы, адаптер, маршруты.
   Агенту отдаю только boilerplate без учебной ценности (CI, конфиги линта,
   .gitignore-мелочи, **фикстуры-данные**) — с явной командой «сделай сам».
2. **Важные понятия и навыки React** Если какой-то из установленных для 
   упрощения компонентов или библиотек упрощает важное свойство или навык в React 
   обязательно проговорить это и дать на выбор возможность сделать упражнение с 
   написанием кода руками а потом использовать компонент.
3. **Лестница подсказок** (для чата и Claude Code): застрял → сначала наводящий
   вопрос или ссылка на концепцию → потом псевдокод → потом фрагмент <10 строк.
   Целый файл — только по явной команде.
4. **Правило 10 минут:** застрял дольше — беру подсказку уровня 1. Это не
   поражение, это экономия мотивации.
5. **Каждый шаг заканчивается видимым результатом и коммитом** (ветка → PR →
   само-ревью → ревью агентом → merge → авто-деплой). Сообщения коммитов —
   человеческие (ADR-0001).
6. **Ревью после каждого шага:** прошу Claude Code проверить написанное мной по
   критерию «Готово» шага + соответствию ADR. Строгость прод-кода, тон наставника.

## АРКА A — учебный срез (фаза 1 программы, слот ~4 ч/нед, недели 1–6)

Скоуп зафиксирован дополнением к программе: каркас, ОДИН вариант шапки, футер,
тело статьи на утверждённых токенах, БЕЗ полки. Веха программы: задеплоенная
SSG-статья к концу недели 4. (Полка возвращается раньше срока — в арке A′,
решение ревизии 2026-07-22.)

### ✅ A0. Скелет и первый запуск (~1–2 ч) — выполнено
- **Учишь:** анатомию App Router — что такое `app/layout.tsx`, `app/page.tsx`,
  зачем каждый файл; TS strict с первой строки.
- **Строишь:** `create-next-app` (TS, App Router, Tailwind) в `journal/`;
  осмотр каждого созданного файла с вопросом «зачем ты».
- **Увидишь:** стартовая страница на `localhost:3000`; правишь текст в
  `page.tsx` — hot reload на глазах.
- **Готово:** dev-сервер работает; strict включён; в репо первый коммит; можешь
  объяснить назначение каждого файла скелета.
- **Читать:** Next docs → Getting Started / Project Structure (по мере, не впрок).

### ✅ A1. Деплой скелета + CD (~1 ч, CI-часть можно агенту) — выполнено
- **Учишь:** прод-сборка vs dev; как выглядит деплой Next.
- **Строишь:** деплой на выбранный хостинг; авто-деплой из main.
- **Увидишь:** СВОЙ публичный URL. С этого дня каждый merge появляется онлайн —
  весь дальнейший план виден не только в localhost.
- **Готово:** публичный URL отдаёт скелет; push в main → авто-деплой.

### ✅ A2. Дизайн-токены + шрифт + живой styleguide (~2 ч) — выполнено
- **Учишь:** Tailwind theme как механизм навязывания токенов (ADR-0004);
  `next/font/local`; почему PT Sans — три веса одной family, а не три family.
- **Строишь:** theme из черновика аудита (layout-audit, п. 2.2); PT Sans woff2 +
  файлы лицензии; страницу `/dev/tokens` — свотчи палитры, ступени типографики,
  радиус (твой личный живой styleguide).
- **Увидишь:** `/dev/tokens` с палитрой и шрифтом журнала — первый экран,
  который выглядит «как наш проект», а не как стартер.
- **Готово:** токены только из theme (линт-запрет arbitrary values — можно
  агенту); PT Sans рендерится всеми весами; лицензия в репо.
- **Читать:** Tailwind theme docs; Next docs → Fonts.

### ✅ A3. Шапка и футер как серверные компоненты (~2–3 ч) — выполнено
- **Учишь:** JSX/TSX, props, композиция; главное — что компонент по умолчанию
  СЕРВЕРНЫЙ: ноль JS в браузер (инверсия относительно старого React).
- **Строишь:** шапку (один вариант, десктоп по макету) и футер строго по макетам
  Main_iDrp — не по CSS des-2016 (правило из аудита). Меню пока ссылка-заглушка.
- **Увидишь:** chrome журнала на своём публичном URL.
- **Эксперимент:** открой DevTools → Network → сколько JS пришло? Запомни цифру —
  сравнишь после A9.
- **Готово:** шапка+футер соответствуют макету; ни одной директивы `'use client'`;
  семантические теги (header/nav/footer — аудит: в легаси их не было).

### ✅ A4. TS-мышцы: домен статьи, Zod, Result (~3–4 ч, строго руками) — выполнено
- **Учишь:** interface vs type, discriminated unions, generics, narrowing,
  `satisfies`, `z.infer` — ровно набор из недель 1–2 программы.
- **Строишь:** типы домена (Article, рубрика как union), Zod-схему фронтматтера
  (обязательные slug, legacyId, даты, alt/width/height картинок — из находок
  аудита; ADR-0006 п. 3); `Result<T, E>` — модуль из программы; vitest-тесты.
- **Увидишь:** зелёные тесты; скорми схеме намеренно битый фронтматтер — получи
  осмысленную ошибку валидации (это будущий контракт контента: битая статья
  роняет сборку).
- **Готово:** схема покрыта тестами на валидные/битые случаи; типы выводятся
  через `z.infer`, дублей руками нет.
- **Читать:** Total TypeScript (unions, generics); zod docs.
- **Заметка по факту:** `description` во фронтматтере — опциональный (pg_dsc
  заполнен на 96.5%); обязательность пересмотреть в B1, когда конвейер начнёт
  «добивать генерацией» недостающие (TODO в схеме).

### ✅ A5. Тело статьи: MDX + prose-слой (~2–3 ч) — выполнено
- **Учишь:** MDX в App Router; @tailwindcss/typography и его кастомизация под
  токены (ADR-0004 п. 3: интерлиньяж 1.6–1.7 вместо легаси 0.7–1).
- **Строишь:** одну РЕАЛЬНУЮ статью (вручную сконвертируй короткое житие или
  притчу из легаси) как .mdx; prose-слой; pull-quote с орнаментальными кавычками.
- **Увидишь:** настоящая статья журнала, красиво свёрстанная, на публичном URL.
  Первый момент «оно живое».
- **Готово:** типографика по токенам; h1 присутствует (в легаси не было — аудит);
  у картинок alt; фронтматтер проходит схему из A4.

### ✅ A6. Динамический маршрут + порт ContentSource (~2–3 ч) — выполнено
- **Учишь:** динамические сегменты `[slug]`, async-компоненты; ports & adapters
  вживую — интерфейс из ADR-0003 (`getArticle`, `listArticles`, `getArticleSlugs`).
- **Строишь:** `/articles/[slug]/` (trailingSlash: true — ADR-0006 п. 1);
  интерфейс ContentSource + filesystem-реализация над MDX. Страница знает только
  интерфейс, MDX напрямую не импортирует.
- **Увидишь:** магия порта: добавь второй .mdx файл — страница появилась сама,
  без единой строчки нового кода.
- **Готово:** обе статьи открываются; прямых импортов MDX из страниц нет
  (проверка ревьюером); типы из A4 сквозные.

### ✅ A7. SSG наглядно: generateStaticParams (~1 ч) — выполнено, веха программы
- **Учишь:** модели рендеринга; чтение вывода `next build` (символы ●/○/ƒ —
  static/SSG/dynamic).
- **Строишь:** `generateStaticParams` по `getArticleSlugs()`.
- **Увидишь:** в билд-логе свои статьи как статические; view-source — полный
  HTML сразу.
- **Эксперимент:** выключи JavaScript в браузере — сайт полностью жив. Это и
  есть «статический путь чтения» из ADR-0005, руками потроганный.
- **Готово:** маршрут статьи ● в билде; понимаешь каждый символ билд-лога.
  **= веха «задеплоенный SSG-маршрут» недели 4 программы.**

### 🔶 A8. SEO-слой: Metadata API + JSON-LD (~2 ч) — в работе
- **Учишь:** generateMetadata, canonical, JSON-LD Article; чем это отличается от
  пустых description легаси (аудит: SEO 1/5).
- **Строишь:** метаданные статьи из фронтматтера; canonical абсолютным URL
  (ADR-0006 п. 1); JSON-LD.
- **Увидишь:** Lighthouse SEO на своей статье — цель ≥95 (критерий программы).
  Прогони Rich Results Test — своя разметка глазами Google.
- **Готово:** Lighthouse SEO ≥95; canonical и JSON-LD валидны.
- **Сделано по факту:** generateMetadata (title/description из фронтматтера
  через порт); дедупликация чтения — `cache()` в публичной точке `@/lib/content`;
  title.template в layout; canonical через route-хелперы (`src/lib/routes.ts`:
  `rootPath`/`articlePath`/`articleUrl` — единый источник базы и путей).
- **Остаток до закрытия:** JSON-LD в статье + валидация Rich Results Test;
  прогон Lighthouse ≥95; layout берёт базу из `rootPath()` (снять дубль).
- **Хвост шага (перенесён в A10):** sitemap.ts / robots.ts; запрет индексации
  превью-окружений.

### A9. Первый клиентский остров: меню-дровер (~2 ч)
- **Учишь:** `'use client'`, граница server/client, гидрация, useState;
  shadcn/ui + Radix (ADR-0004 п. 2) — доступность бесплатно.
- **Строишь:** меню-дровер (shadcn Sheet) по макету Menu — остров-лист в
  серверной шапке. Бонус-остров: дата в шапке (локальное время читателя —
  ADR-0005 п. 7).
- **Увидишь:** живой интерактив; Network-таб — JS пришёл только для острова
  (сравни с цифрой из A3).
- **Эксперимент:** убери `'use client'` — прочитай и пойми ошибку; верни.
  Попробуй передать функцию из серверного компонента в клиентский — пойми,
  почему нельзя.
- **Готово:** дровер работает с клавиатуры (Tab/Esc — Radix даёт даром, в легаси
  этого не было); `'use client'` только в островах-листьях.

**Итог арки A:** задеплоенный срез — chrome + токены + 2+ реальные статьи SSG +
SEO ≥95 + один остров. Все критерии среза фазы 1 закрыты. Дальше по программе —
фокус на интервью; стройка возвращается в фазе 2.

## АРКА A′ — статья и главная по дизайну (ревизия 2026-07-22)

Цель арки: страница статьи и главная 1:1 с утверждёнными макетами
(`design_final_pict/`: `article/Statiya_3_1980-1`, `main/Glavnaya_Portal_2`

пойдут реальные данные, — «подключить реальные данные» означает смену
адаптера/вызова, а не перевёрстку.

    структура панели (рубрики, список статей с анонсами) на фикстурах;
    реальные данные рубрик — B2.
- **Решение по ходу:** промежуточный брейкпоинт 1024–1280 (пробел №5) —
  принять и записать (сверить с ADR-0004 п. 6).
- **Увидишь:** статья корректна на всех трёх ширинах макетов; 404 в стиле
  журнала.
- **Готово:** 320/768/1600 соответствуют макетам; 404 отдаёт HTTP 404;
  Lighthouse (SEO и Performance) не просел относительно A8.

### A13. Главная-портал на фикстурах (~3–4 ч + мини-ADR)
- **Учишь:** динамические края против статического пути чтения (ADR-0005) на
  живом примере; проектирование «до вёрстки»: сначала решение, потом код.
- **Строишь:** (1) мини-ADR по динамике главной: блок дня и «Читальный зал»
  (в легаси — 3 случайные статьи) — варианты: детерминированный выбор по дате
  + суточная ревалидация, клиентский остров, отложить; зафиксировать выбор и
  цену; (2) главная по `Glavnaya_Portal_2` + мобильные ревизии: блок дня,
  календарь-«колесо» (статичный серверный; интерактив — при календаре именин
  в C3), «Читальный зал» 2×2, ряды карточек, лента событий, товарные ряды
  (BookShelf) — на фикстурах (CC), за портами, которые в B2 получат реальные
  данные; выровнять сетку 1600 vs 1980 (пробел №10).
- **Увидишь:** главная журнала как в макете, на публичном URL.
- **Готово:** соответствие макету (1600 + 320/768); ADR по динамике записан;
  смена фикстур на реальные данные в B2 не потребует правок разметки
  (проверка ревьюером: страница знает только порты).

**Итог арки A′:** статья и главная 1:1 с дизайном на брейкпоинтах макетов;
полка живая на фикстурах; sitemap/robots в проде; JS в браузере — по-прежнему
только острова (меню, дата, поиск-оверлей).

## АРКА B — вертикаль недель 9–10 (тезисно; детализация — перед стартом фазы 2)

Шаги крупнее: навык уже есть, учишься применённому систем-дизайну. Каждый шаг —
реализация конкретного ADR, читать его перед стартом.

- **B1. Конвейер на подвыборке** (15–20 разнотипных статей: житие, притча, без
  слага, дубль слага, с кросс-ссылками, с картинками). iconv строго без -c
  (дополнение, реш. 3), HTML→MDX, слаг-политика и legacyId (ADR-0006 п. 3),
  отчёт конвейера. Учишь: Node-скриптинг на TS, стримы, кодировки.
  Увидишь: реальные статьи из дампа в браузере + отчёт. Здесь же: пересмотр
  опциональности `description` (заметка A4) — конвейер «добивает генерацией».
  Заметки ревизии 24.07: pull-quote конвейер не распознаёт — в легаси-HTML
  разметки цитат нет; выделение текста в цитаты — редакционная работа после
  конвертации (компонент из A5/A11 принимает текст руками), в отчёт
  конвейера — счётчик статей без единой цитаты (кандидаты на редактуру).
  Подписи изображений: правило «у каждой картинки — подпись»; конвейер
  берёт подпись из легаси (title/соседний текст), при отсутствии —
  TODO-строка в отчёте, не молчаливый пропуск.
- **B2. Индекс метаданных + списки** (`/zhurnal/`, `/zhitiya/<mesyac>/`,
  `/arhiv/`, пагинация `.../page/<n>/` — ADR-0006 п. 2; индекс — ADR-0005 п. 2).
  Увидишь: живые ленты рубрик (к этому моменту макет рубрики должен быть закрыт
  через Claude Design — пробел №1 аудита). **Дополнено ревизией:** перевести
  главную (A13) с фикстур на реальные данные индекса — критерий «Готово» B2.
  **Дополнено ревизией 24.07:** ссылки шапки «Журнал», «Жития Святых» и
  контент дровера переходят со стадии заглушки/фикстур на внутренние
  маршруты и реальные рубрики (стадия 3 политики ссылок из мини-ADR A10).
- **B3. Кэш-теги в адаптере + /api/revalidate + тест** (ADR-0005 п. 3–4).
  Учишь: Data Cache, revalidateTag, SWR-семантику. Увидишь: точечную пересборку
  страницы через curl в прод-режиме (`next build && next start`).
- **B4. Middleware редиректов + первый strangler-прокси** (ADR-0006 п. 4–5;
  passthrough Content-Type с charset=windows-1251 — дополнение). Увидишь:
  `curl -I` старого URL → 301 одним хопом; неизвестный `-lib` → passthrough.
- **B5. Полный прогон конвейера + замер сборки.** ~2000 страниц в билд-логе;
  время сборки против оценки — петля «спроектировано ↔ замерено» (ADR-0005).
- **B6. ISR-механика полки** (дополнение, реш. 2; **скорректировано ревизией:**
  BookShelf и MockProductSource уже построены в A10–A11). Здесь: `revalidate`
  ~1 ч / on-demand по тегу `products` (ADR-0005), проверка «статья остаётся
  SSG, цены не вшиты в билд намертво»; контракт готов к смене адаптера на
  `LegacyHttpProductSource` (HTTP-endpoint на легаси-PHP, UTF-8 JSON по
  контракту фикстур — ADR-0008); мост к вертикали магазина.

## АРКА C — именины (старт после B5; тезисно, детализация перед стартом)

Самостоятельный раздел дизайна: 4 шаблона + собственный сайдбар
(`namesday/Imeniny_3-1..4` + мобильные `Imeniny_4_320-1..4`), собственная
модель данных (таблицы `cal`, словари имён dic 29/32, статьи type=14/15 —
legacy-map п. 4.4). Слаги — транслитом, непрерывность с легаси
(`imeniny-<imya>-lib<id>/` → новая политика по ADR-0006).

- **C1. Модель данных именин + ADR.** Спроектировать домен (имя, даты памяти,
  связь со статьями-житиями) и решить ADR-ом: расширение `ContentSource` или
  отдельный порт `NameDaySource` (критерий — санитарная проверка ADR-0007);
  кусок конвейера для cal/словарей. Учишь: моделирование унаследованного
  домена; повторение цикла «схема → порт → адаптер» на данных другой формы.
  Увидишь: типизированные данные именин, тесты зелёные.
- **C2. Шаблоны буква / месяц / имя (SSG).** Маршруты раздела именин по
  ADR-0006; `generateStaticParams` на сотнях страниц — первая проверка SSG
  на объёме до B5-масштаба; вёрстка по макетам `Imeniny_3-2..4` + 320;
  метаданные/JSON-LD по образцу A8. Пробел №8 («полное описание имени» —
  макета нет) — закрыть через Claude Design или зафиксировать отсрочку.
  Увидишь: живые страницы имён/букв/месяцев в билд-логе как ●.
- **C3. Хаб именин + календарь-остров.** Макет `Imeniny_3-1`; календарь на
  shadcn/Radix (ADR-0004 п. 2) как клиентский остров; «именины сегодня» —
  динамический край: зафиксировать TZ-политику (открытый пункт ADR-0005 —
  «TZ именинных виджетов зафиксировать при их реализации»). Увидишь: раздел
  именин жив целиком, календарь кликается, статический путь чтения не сломан.

**Итог арки C:** раздел именин по всем четырём шаблонам, свой конвейер данных,
календарь-остров; TZ-политика записана в ADR-0005.
