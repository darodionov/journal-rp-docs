# Журнал — kickoff-бриф

> Назначение: сжатый контекст проекта для рабочих сессий (в чате и в Claude Code).
> Кладётся в `journal-docs/briefs/journal-kickoff-brief.md`. Это источник для ADR-0002 (стек).

## Контекст в одном абзаце

Переписываем legacy-сайт (PHP 7 / Silex, местами Vue/jQuery, MySQL без PDO, запросы в коде)
на **единый стек Next.js**. Сайт — три продукта: **журнал** (контент, критичен для SEO),
**магазин** (каталог + транзакции), **конфигуратор рамок** (клиентский SPA-остров).
Начинаем с журнала — самой чистой вертикали. Метод: **project-first** (теория берётся прямо
перед реализацией конкретной заботы и замеряется после), миграция по схеме **strangler-fig**,
каждое значимое решение фиксируется как **ADR**. Двойная цель: рабочий продукт, который
«не стыдно показать», + прокачка систем-дизайна/архитектуры и глубокое освоение Next.js.

## Решено твёрдо

- **Единый стек**: Next.js (**App Router**) + **TypeScript strict** на весь проект. Не Pages Router.
- **Первая вертикаль**: журнал. Модель рендеринга — **SSG + ISR**; статический путь чтения
  раздаётся с **CDN**.
- **Контент на старте**: **MDX в репозитории** + валидация фронтматтера через **Zod**
  (типизированный контент, собранный руками).
- **Дизайн-система**: Есть разработанный готовый дизайн в картинках и уже в html/js файлах. его мы используем как основу, вид. Сами файлы надо будет переписать. **Tailwind CSS + shadcn/ui** — общая, переиспользуется будущим магазином.
  Готовый HTML/JS-дизайн переносится в эти компоненты.
- **Данные**: **Postgres + Drizzle** — только для динамических краёв, НЕ на пути чтения статьи.
- **SEO-инфраструктура** — часть архитектуры журнала, не «допилим потом»: Metadata API,
  `sitemap.xml`, `robots.txt`, JSON-LD, canonical-URL, карта редиректов со старых адресов.

## Открыто / решаем по ходу («не категоричное»)

- **Источник контента**: MDX-в-репозитории → возможный переход на headless-CMS (**Payload**
  на TS, стыкуется с Next вплоть до запуска в том же процессе; либо **Sanity**). Триггер
  перехода — появление не-технических авторов или потребность в богатом редакторе/ролях/расписании.
  Это **триггер, а не дата**. → принцип зафиксирован в ADR-0003.
- **Поиск**: внешний сервис (**Meilisearch / Typesense / Algolia**) против **Postgres FTS**.
  Обоснованный выбор под масштаб и бюджет — решение своей фазы. От хостинга даром не приходит.  → раздельность хранилищ — в ADR-0003; конкретное решение своей фазой.
- **Граница client/server**: какие части журнала — серверные компоненты (по умолчанию), что
  уходит в клиентские острова-листья. Принцип: держать границу как можно **ниже** по дереву.
- **Node vs Edge рантайм**: Edge — точечно для middleware редиректов и лёгкой динамики близко
  к пользователю. Детали при проектировании.
- **Динамические края** (счётчик просмотров, «читают сейчас»): где живут данные, чтобы НЕ
  утягивать статью в динамику.
- **Стратегия ISR-инвалидации**: `revalidate` по времени против on-demand по тегам
  (`revalidateTag` / `revalidatePath`). Сердце архитектуры — проектируем первым.

## Архитектурный костяк (инвариант)

Устоял при смене фреймворка Astro → Next — значит, он несущий, а фреймворк вторичен:

**Статический путь чтения через CDN + инкрементальная регенерация (ISR) + аккуратные
динамические края + отдельный слой поиска + SEO/редирект-инфраструктура.**

## Оси масштабирования журнала (что реально масштабируем)

Для чистого SSG «высокая нагрузка на чтение» решается CDN почти бесплатно. Настоящие оси:

1. **Масштаб изменения, а не чтения** (пересборка 200k статей) → ISR.
2. **Свежесть vs статика** → динамические края.
3. **Полнотекстовый поиск** → отдельное решение.
4. **Медиа в объёме** → оптимизация и доставка изображений.
5. **Миграция + непрерывность SEO** → карта редиректов, canonical, sitemap, structured data.
   **Самое рискованное место переезда.**

## Ближайшие шаги проектирования (порядок от несущего к периферии)

1. **Поток сборки и ISR-инвалидации** — что пре-рендерится при сборке (`generateStaticParams`)
   vs ISR по требованию; как редактирование статьи триггерит `revalidateTag`; где граница
   «пересобрать одну страницу, не трогая сайт».
2. **Стратегия миграции с PHP** (strangler-fig) — как маршруты журнала перехватываются на новое,
   пока старый PHP отдаёт остальное; карта редиректов и сохранение SEO.
3. **Граница client/server** — серверные компоненты по умолчанию, клиентские острова-листья.
4. **Динамические края** — где живут данные просмотров/«читают сейчас».
5. **Слой поиска** — внешний сервис vs Postgres FTS.

## Метод работы (две поверхности, один Claude, доки как мост)

- **Чат (claude.ai)** = студия архитектора: систем-дизайн, ADR, выбор из вариантов, разбор
  механик (RSC/ISR/инвалидация), ревью. Репозиторий не мутируется.
- **Claude Code** = стройплощадка: реализация в репозитории — скелет, ISR-маршруты, редиректы,
  MDX+Zod, билд/тесты/коммиты.
- **Мост** = документы в репозитории: `CLAUDE.md` (терсный поведенческий контракт) +
  `journal-docs/adr/*` (решения с trade-offs). Решение в чате → в доки → Claude Code исполняет
  → ревью в чате.
- **Правило**: Claude Code не принимает архитектурные решения молча. Развилку вне доков выносит
  на решение (в момент или в чат — как ADR).
- **Топология репозиториев** зафиксирована в ADR-0001 (раздельные код / документация / обвязка).
