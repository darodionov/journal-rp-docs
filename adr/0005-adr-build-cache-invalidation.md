# ADR-0005: Поток сборки и инвалидации кэша

- Статус: Предложено
- Дата: 2026-07-08

## Контекст
Журнал рендерится по модели SSG+ISR со статическим путём чтения через CDN (ADR-0002,
бриф). Корпус по legacy-БД: ~1515 журнальных статей (1199 житий, 178 именинного куста,
~140 хвоста) + 39 архивных + ~40 генерируемых указателей — порядка 2000 статических
страниц (`legacy-rubrics.md`). Публикации редкие, через репозиторий; переход на CMS
намечен к выходу в прод (триггер ADR-0003). Товарные блоки вшиты в шаблоны (полка
`<BookShelf>`, сайдбар, ряды — дополнение к программе, реш. 2; дизайн-аудит, п. 6) и
получают данные через `ProductSource` со сменными реализациями mock → MySQL(ro) →
Medusa. Дизайн поимённо называет динамические поверхности: дата в шапке, «именины
сегодня», календарь, случайное имя, лента событий.

Кэш-модель Next: Full Route Cache (HTML маршрута; наполняется при сборке или при
первом запросе) и Data Cache (данные с тегами; маршрут автоматически зависит от тегов
функций, которые вызвал при рендере, — граф зависимостей строится неявно). Рычаги:
`revalidate` (TTL, семантика stale-while-revalidate) и `revalidateTag`/`revalidatePath`
(точечно). В Next два поколения кэш-API (fetch-теги/`unstable_cache` и
`'use cache'`/`cacheTag`) — механика одна.

## Решение
1. **Рендеринг:** полный пре-рендер корпуса при сборке (~2000 стр.,
   `generateStaticParams`). Списки — первые страницы при сборке, хвост пагинации и
   тег-страницы on-demand (`dynamicParams`). Параметр «топ-N при сборке» заложен,
   включается по замеру (ориентир пересмотра: сборка стабильно >10 мин или корпус
   >5–10 тыс. страниц).
2. **Индекс метаданных:** один проход по корпусу за сборку (slug, заголовок, даты,
   тип/рубрика, даты памяти); его читают списки, sitemap, RSS, «по теме». Прямых
   чтений «всех MDX» из страниц нет.
3. **Инвалидация сейчас:** деплой-как-инвалидация (git-контент; деплой атомарно
   заменяет контент и сбрасывает кэш). Endpoint `POST /api/revalidate` (секрет в
   заголовке; вход: тип события + slug/id → маппинг на теги) существует и покрыт
   тестом с первого дня, в git-режиме в потоке публикации не участвует.
4. **Схема тегов — два уровня + товарный домен:** `article:{slug}` (страница статьи);
   `articles` (все списковые поверхности: главная, рубрики, теги, пагинация, sitemap,
   RSS, «по теме»); `products` (+ `product:{id}` при доказанной нужде). Теги живут
   внутри адаптеров (`ContentSource` — ADR-0003; `ProductSource` — дополнение, реш. 2);
   страницы о тегах не знают. Публикация статьи X → `revalidateTag('article:X')` +
   `revalidateTag('articles')`.
5. **Принцип соответствия:** механизм инвалидации следует за способностью источника
   сигналить об изменениях. Git → деплой; legacy MySQL(ro) — немой источник → только
   TTL (~1 ч у полки); Medusa/CMS → webhook → `/api/revalidate` → теги, TTL остаётся
   страховочным.
6. **TTL:** списки — страховочный ~1 ч; статья без товарных блоков — без TTL; статья
   с полкой наследует интервал полки на уровне маршрута (route revalidate = минимум по
   фетчам) — осознанно: перечитывание текста из адаптера дёшево.
7. **Динамические края — правило:** данные, чья истина зависит от запрашивающего или
   момента запроса, не живут в общем статическом HTML. Дата в шапке — клиентский
   остров (локальное время читателя); случайное имя — клиентский остров (per-request);
   «именины сегодня»/календарь — серверный фрагмент с revalidate до полуночи (TZ
   зафиксировать при реализации, ориентир MSK) либо остров с per-day-кэшированным
   эндпоинтом; «по теме»/«события» — кэшируемый фрагмент с тегом `articles` + TTL,
   вне HTML статьи (каскад «правка соседа инвалидирует статью» отрезан by design).
8. **Путь чтения статьи не использует request-scoped API** (`cookies()`/`headers()`) —
   иначе маршрут тихо становится динамическим. Персональное/живое — только острова и
   изолированные фрагменты (согласуется с ADR-0004: интерактив — листья).
9. **Инвалидация до внешнего кэша:** пока CDN без собственного долгого TTL — он
   амортизатор (короткий edge-TTL + SWR). Если появится CDN с длинным TTL —
   revalidate-handler обязан дёргать его purge API. Конкретика — при выборе хостинга.
10. **Кэш локален инстансу:** второй инстанс не поднимается без общего cache handler
    (Redis/S3-совместимого).
11. **Предпросмотр:** сейчас — preview-деплой ветки; при CMS — draft mode (обход кэша
    только для редактора).
12. Конкретная сигнатура кэш-API (fetch-теги vs `'use cache'`/`cacheTag`) выбирается
    при реализации по текущей версии Next; ADR фиксирует механику (теги, SWR,
    on-demand), не сигнатуры.

## Рассмотренные альтернативы
- **Чистый SSG с полным ребилдом на каждое изменение, без тегов/ISR** — проще всего,
  но замыкает архитектуру на git-контент: переход на CMS (триггер — прод) потребовал
  бы перепроектирования; динамические края всё равно нужны.
- **Тонкая грануляция тегов** (`category:{slug}`, `author:{id}`, `related-to:{slug}`) —
  точнее, но раздувает граф зависимостей и порождает класс багов «забытая инвалидация»
  (залипшая страница — невидимый баг). На корпусе ~2000 переплата широкого `articles`
  дёшева (пересборка списков — чтение индекса метаданных), SWR прячет её от читателя.
  Утончать только по замеренной боли.
- **SSR + SWR-кэш без SSG** (всё on-demand) — убирает сборку, но первый читатель
  каждой страницы ждёт рендер; «статический путь чтения» перестаёт быть гарантией by
  construction; SEO-риск на холодных страницах.
- **Внешний кэш-слой (Varnish/CDN-only) поверх SSR** — смещает сложность в
  инфраструктуру и ручную purge-логику; дублирует то, что Next даёт из коробки, без
  выигрыша для соло-эксплуатации.

## Последствия
- Плюсы: переход на CMS меняет вызывающего инвалидацию (webhook вместо деплоя), кэш-слой
  не трогается; товарные поверхности покрыты доменом `products`, смена реализаций
  `ProductSource` (mock → MySQL → Medusa) тегов не меняет; читатель всегда получает
  кэш/статик (SWR прячет пересборки); класс багов «забыли инвалидировать список» закрыт
  широким `articles`.
- Минусы / компромиссы: правка одной статьи пересобирает все списковые поверхности
  (осознанная переплата за простоту); свежесть полки ограничена TTL ~1 ч (приемлемо —
  чекаут валидирует цену на своей стороне, дополнение реш. 2); статья с полкой
  ревалидируется целиком по интервалу полки; ISR-кэш локален — горизонтальное
  масштабирование гейтится общим handler'ом; два поколения кэш-API Next — риск смены
  сигнатур при апгрейдах.
- Дальнейшие шаги: реализовать в вертикали чтения (недели 9–10); замерить полную сборку
  на реальном корпусе и сверить с оценкой (петля «спроектировано ↔ замерено»); включить
  «топ-N» при пробитии порога; при CMS-триггере подключить webhook к `/api/revalidate`
  (отдельный ADR выбора CMS-продукта); при втором инстансе — общий cache handler; при
  CDN с длинным TTL — purge-механика; TZ именинных виджетов зафиксировать при их
  реализации; **проверить по дампу живость композиции `grid_tp != 0` среди мигрируемых
  типов** — если жива, это зависимость статья→статья: конвейер разворачивает композицию
  (bake) либо встроенные фрагменты получают собственные теги `article:{slug}` доноров.
