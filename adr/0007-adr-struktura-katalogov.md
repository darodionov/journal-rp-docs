# ADR-0007: Структура каталогов приложения журнала

- Статус: Принято
- Дата: 2026-07-19

## Контекст

Шаг A6 вводит порт `ContentSource` (ADR-0003) — впервые встаёт вопрос, где
физически живут порт, адаптер, схема и сами данные. Стартовая структура после
A5 имеет три дефекта: (а) `.mdx`-контент лежит внутри `src/app/` — контент
склеен с роутером, файл *является* маршрутом, шов для смены источника
невозможен; (б) коллизия имени `content`: `src/content/` — это код (Zod-схема),
а место для данных тоже просится называться `content`; (в) размещение порта и
адаптера не определено.

Мерило решения: промышленность структуры измеряется не количеством папок, а
тем, какие изменения она делает дешёвыми. Известные из ADR будущие изменения:
смена источника контента (ADR-0003), второй домен `ProductSource`
(дополнение к программе, реш. 2), конвейер миграции (арка B).

## Решение

Целевое дерево (показаны только структурно значимые узлы):

```
journal/
├── content/                        # ДАННЫЕ — вне src/, не модули компилятора
│   └── articles/
│       └── <slug>.mdx              # имя файла = слаг (контракт fs-адаптера)
├── public/
│   └── images/<slug>/...           # картинки статей
└── src/
    ├── app/                        # ТОНКИЙ СЛОЙ ДОСТАВКИ — только через порт
    │   ├── articles/
    │   │   └── [slug]/
    │   │       └── page.tsx        # потребитель: import from '@/lib/content'
    │   ├── dev/tokens/             # живой styleguide (A2)
    │   ├── layout.tsx
    │   └── page.tsx
    ├── components/
    │   ├── layout/                 # header.tsx, footer.tsx
    │   ├── mdx/                    # pull-quote.tsx, signature.tsx
    │   └── ui/
    ├── fonts/
    └── lib/
        ├── result.ts               # общая утилита — вне доменных модулей
        └── content/                # МОДУЛЬ ДОМЕНА «КОНТЕНТ»
            ├── index.ts            # единственная публичная точка входа
            ├── content-source.ts   # ПОРТ (ADR-0003): только доменные типы
            ├── filesystem-source.ts# АДАПТЕР над content/articles/
            ├── schema.ts           # Zod-схема = домен (типы через z.infer)
            ├── schema.test.ts
            ├── frontmatter.test.ts
            └── __fixtures__/
```

Пункты решения:

1. **`content/` в корне репозитория — данные, вне `src/`.** MDX-файлы статей в
   `content/articles/`; имя файла = слаг (первый неявный контракт
   filesystem-адаптера). Данные не проходят через компилятор как модули — их
   читает адаптер с диска. Физическая граница «код/данные» совпадает с
   архитектурной.
2. **`src/lib/content/` — модуль домена «контент».** Внутри: `schema.ts`
   (контракт данных, переезд из `src/content/`), `content-source.ts` (порт),
   `filesystem-source.ts` (адаптер), тесты и фикстуры, `index.ts` —
   единственная публичная точка входа модуля.
3. **Правило импортов:** потребители пишут `import ... from '@/lib/content'`
   и никогда — глубокие пути до реализаций. Порт импортирует только доменные
   типы; появление в нём `fs`/`mdx` — дефект ревью.
4. **`src/app/` — тонкий слой доставки.** Маршруты потребляют контент только
   через порт; `.mdx` в `app/` не живёт. Маршрут статьи —
   `app/articles/[slug]/` (URL-политика — ADR-0009).
5. **Общие утилиты (`result.ts`) — в `src/lib/`, вне доменных модулей:** ими
   будет пользоваться и будущий `ProductSource`.
6. **Отдельный `src/domain/` не заводится.** Типы домена рождаются из Zod
   через `z.infer` — `schema.ts` и есть домен контента; папка ради реэкспорта —
   церемония.
7. **Границы держатся ревью** (Claude Code, сверка с этим ADR) + линт-правилом
   на глубокие импорты (boilerplate, можно агенту).

## Триггеры пересмотра

Структура принимается вместе с условиями своей смерти. Каждый пересмотр —
новым ADR со ссылкой сюда, не молчаливой правкой.

| Триггер | Ожидаемое изменение |
|---|---|
| Второй домен (`ProductSource`, фаза 2, нед. 9–11) | Поднять общее между доменами; возможно, выделить общий доменный слой |
| Второй потребитель домена (admin-приложение, отдельный сервис) | Монорепо-пакеты внутри `journal/`: `packages/content` + `apps/*` (Turborepo/pnpm workspaces). Ортогонально ADR-0001 — топология *репозиториев* не меняется |
| Рост команды (>1 человека в коде) | Границы из ревью-соглашения становятся tooling-контрактом: `eslint-plugin-boundaries` / `dependency-cruiser`, красный CI на нарушение |

## Рассмотренные альтернативы

- **MDX внутри `app/` (статус-кво A5)** — отвергнуто: контент склеен с кодом,
  «добавил файл — страница появилась» работает через магию роутера, а не через
  порт; подключение CMS требует переписывания страниц, что прямо противоречит
  ADR-0003.
- **Слоистая clean-architecture (`entities/usecases/gateways/...`), интерфейс
  на каждый класс, DI-контейнер** — отвергнуто: перерасход абстракции для
  сайта-читалки. Санитарная проверка: у каждой абстракции должен быть
  названный сценарий, который она удешевляет; у `ContentSource` он записан в
  ADR-0003, у слоёв поверх него — отсутствует.
- **Пакеты (`packages/content`) сразу** — отвергнуто: пакет ради единственного
  потребителя — церемония без выгоды; заведено как триггер пересмотра.

## Последствия

- Плюсы: направление зависимостей читается по import-путям; смена источника
  контента локализована в одном модуле; данные мигрируют в CMS без правок
  кода страниц; структура растёт по записанным триггерам, а не переделками.
- Минусы / компромиссы: границы пока держатся дисциплиной ревью, а не
  инструментом (приемлемо для соло; линт-правило — дёшево и заводится сразу);
  «имя файла = слаг» — неявный контракт, который при переходе на CMS заменится
  явным полем слага в источнике.
- Дальнейшие шаги: переезд по шагам A6 (см. learning-build-plan);
  линт-правило на глубокие импорты — задача агенту.
