# ADR-0004: Стилевое решение нового стека — Tailwind CSS + shadcn/ui

- Статус: Предложено
- Дата: 2026-07-07
- Обновлено: 2026-07-10 — п. 6 «Адаптивная стратегия и брейкпоинты»,
  п. 7 «Версия Tailwind (v4, CSS-first)»
- Обновлено: 2026-07-10 — п. 1 и п. 4 приведены к решениям дизайн-системы
  (Claude Design): цвет — утверждённый микс «канон + наши значения»; шрифт —
  две гарнитуры (PT Sans + PT Sans Narrow)
- Обновлено: 2026-07-23 — п. 2: Base UI вместо Radix

## Контекст
Дизайн утвержден и сохраняется (макеты `../graphic_design/Main_iDrp`, разбор в
`../design/graphic/main-idrp-design-audit.md`). Аудит верстки-референса
`legacy/des-2016` (`../audit/layout-audit.md`) дал вердикт «переверстать»:
код стилей непереносим (две параллельные CSS-ветки со 145 дублирующимися
селекторами, float-грид, все размеры в px, классы-краски `.blue`/`.brown`
без семантики - 1041 использование), при этом дизайн-токены извлекаются чисто
(~8 цветовых ролей с дрейфом, 6-8 ступеней шрифта, один радиус 3px).

Ограничения: стек Next.js (App Router) + TypeScript strict (ADR-0002);
журнал мигрирует первым и SEO-критичен (Lighthouse SEO >= 95); статический
путь чтения статьи неприкосновенен (ADR-0003); разработка соло с Claude Code;
дизайн-систему собираем в Claude Design до верстки. Тело статьи приходит как
контентный HTML/MDX из пайплайна - его типографика не может жить в классах
компонентов. Верстки магазина и конфигуратора еще нет - решение должно их
не блокировать, но принимается по данным журнальной вертикали.

## Решение
1. **Tailwind CSS** - основное стилевое решение для всех компонентов.
   Источник значений - **токены дизайн-системы (Claude Design)**, не аудит
   напрямую. По цвету утверждён **микс** (решение пункта 1 дизайн-системы):
   из канона аудита берём бирюзу `#65c6cd` и приглушённый `#939598`;
   остальное — наши значения: коричневый `#4d2b17`, терракота `#d4a187`,
   текст `#565350`, разделители `#e1e1e1`, фон страницы белый + карточки
   `#f1f1f1`. Радиус - единый 3px. Эти токены фиксируются в `@theme` и
   являются единственным источником значений; произвольные значения
   (`text-[#...]`, `p-[13px]`) запрещаются линт-правилом. Замечание: часть
   наших цветов аудит квалифицирует как «дрейф» - это осознанное
   отклонение в пользу утверждённой палитры дизайн-системы.
2. **shadcn/ui (Radix-примитивы)** - для интерактивных компонентов (меню-
   дровер, оверлей поиска, табы, формы, календарь именин): закрывает
   клавиатурную доступность и фокус-менеджмент, которых в легаси нет.
3. **Типографика статьи** - отдельный prose-слой: `@tailwindcss/typography`
   с конфигурацией под токены (PT Sans, интерлиньяж 1.6-1.7 вместо
   легаси 0.7-1, pull-quote, врезки). Это единственный глобальный
   стилевой контракт с контентом.
4. **Глобальный слой**: Tailwind preflight вместо legacy normalize.css;
   шрифты через `next/font/local` — **две гарнитуры** (решение пункта 3
   дизайн-системы): **PT Sans** основная (woff2, три файла — веса
   400/700/italic) + **PT Sans Narrow** для подписей/подзаголовков-лейблов
   (отдельный woff2). В `@theme` — две переменные: `--font-sans` и
   `--font-narrow`. (Легаси использовал три несвязанные family; здесь — две
   осознанные роли: текст и узкое начертание для подписей.)
   Лицензии обеих гарнитур (PT Sans / PT Sans Narrow) — в репозитории.
5. Легаси-CSS не переносится ни в каком виде; HTML des-2016 используется
   только как референс структуры блоков, источник истины - макеты.
6. **Адаптивная стратегия и брейкпоинты.** Двухслойная модель:
   viewport-брейкпоинты решают раскладку уровня страницы, контейнерные
   запросы - внутреннюю раскладку компонентов.
   - **Viewport: ровно два брейкпоинта** - `md: 48rem` (768px) и
     `lg: 64rem` (1024px). Они соответствуют якорям макетов Main_iDrp
     (320 / 768 / 1600); диапазоны: до 768 - мобильная раскладка,
     768-1024 - планшетная, свыше 1024 - десктопная. Легаси-дрейф точек
     (950/951/1223/1224/1280/1281) не переносится.
   - **Крупные экраны без брейкпоинта:** десктопный макет (1600-1980)
     обслуживается центрирующим контейнером `max-width: 80rem` (1280px)
     с боковыми полями - после 1280 растет экран, но не контент.
     Отдельной точки на 1280/1600 нет.
   - **Дефолтные брейкпоинты Tailwind урезаются** до двух выбранных
     (в `@theme`: `--breakpoint-sm/xl/2xl: initial`). Набор становится
     самодокументируемым: каждая точка соответствует макету; агент не
     может повесить `xl:` там, где дизайна не существует. Цена: чужие
     сниппеты с `sm:`/`xl:` молча теряют эффект - принимается осознанно.
   - **Единицы брейкпоинтов - rem** (требование единообразия единиц
     Tailwind v4 + лечение px-болезни легаси: 1381 px-значение, 0 rem).
   - **Компоненты в нескольких контекстах** (карточка материала: крупная /
     оверлей / мини; товарная карточка: сайдбар / ряд / карусель)
     адаптируются контейнерными запросами (`@container`, ядро Tailwind
     v4), а не viewport-точками - одна карточка, ноль классов-модификаторов
     контекста (антириск «классов-красок» из аудита).
   - **Флюидная типографика** (`clamp()`) для заголовков статьи и
     крупных ступеней prose-слоя - вместо промежуточных брейкпоинтов
     (заменяет легаси-прыжки 2em/2.3em/80px).
   - Конфигурация брейкпоинтов - в CSS через `@theme`
     (`--breakpoint-*`), не в JS-конфиге (в Tailwind v4 `screens`
     удален; черновик theme в layout-audit.md п. 2.2 в части `screens`
     устарел и заменяется этим пунктом).
7. **Версия Tailwind: v4 (CSS-first).** Пин: Tailwind CSS v4 (актуальная
   линия 4.3.x на 07.2026). Причина фиксации: обучающие данные генераторов
   кода и большинство туториалов по умолчанию выдают v3-идиому — это
   систематический источник ошибок. Красный флаг: любой сгенерированный
   `tailwind.config.js` с `theme.extend` или директивы
   `@tailwind base/components/utilities` — не v4, откатывать.
   Ключевые расхождения v3 → v4 (используем правую колонку):
   - Конфиг: `tailwind.config.js` → CSS через `@import "tailwindcss"` +
     `@theme { --* }` (JS-конфиг по умолчанию не создаём).
   - Подключение: три `@tailwind`-директивы → одна `@import "tailwindcss"`.
   - Токены: `theme.extend.{colors,fontSize,...}` → CSS-переменные
     `--color-*`, `--text-*`, `--breakpoint-*`, `--radius-*`, `--font-*`
     (включая `--font-sans` и `--font-narrow` — см. п. 4).
   - Брейкпоинты: `screens{}` и директива `@screen` удалены →
     `--breakpoint-*` (см. п. 6).
   - Контейнерные запросы: в ядре → плагин
     `@tailwindcss/container-queries` НЕ ставим.
   - Сканирование классов: массив `content[]` не нужен (авто-детект);
     при необходимости — директива `@source`.

## Рассмотренные альтернативы
- **CSS Modules с сохранением существующих классов** - отвергнуто: выгода
  этого пути - реюз готовых стилей, а реюзать нечего (классы не несут
  семантики, общие блоки существуют в двух конфликтующих копиях); получили
  бы ручное сопровождение токенов и перенос дрейфа в новый стек.
- **Чистый CSS + custom properties (без фреймворка)** - жизнеспособно, но
  дисциплина токенов, состояний и адаптивности держится только на
  соглашениях; для соло-разработки с генерацией кода это медленнее и
  дрейфоопаснее, чем энфорс через theme.
- **CSS-in-TS (vanilla-extract и подобные)** - типобезопасность токенов
  привлекательна, но добавляет сборочную сложность, отсекает экосистему
  shadcn/ui и не дает преимуществ для SSG-пути (стили и так статичны).
- **Готовые UI-киты (Bootstrap/Mantine/MUI)** - чужой визуальный язык;
  дизайн уже утвержден и самобытен (дореволюционная орфография, орнаменты),
  переопределение кита дороже сборки из примитивов.
- **Дефолтный набор брейкпоинтов Tailwind (sm/md/lg/xl/2xl)** - отвергнуто:
  640/1280/1536 не соответствуют ни одному макету; лишние точки провоцируют
  «дизайн на глазок» в неспроектированных диапазонах. Совместимость с чужими
  сниппетами ценится ниже самодокументируемости набора.
- **Промежуточный брейкпоинт sm: 480px** - отвергнуто: между 320 и 768
  макетов нет; перестроение сеток карточек в этом диапазоне - задача
  контейнерных запросов на уровне компонента, а не viewport-точки.
- **Брейкпоинт на 1280/1600 под десктопный макет** - отвергнуто: макет 1600
  описывает холст, а не точку перелома; строка на всю ширину 1600 нечитаема.
  Решается max-width-контейнером, не медиа-запросом.

## Последствия
- Плюсы: токены навязываются механически (главный антириск аудита - россыпь
  «красок»); a11y-дыры легаси не воспроизводятся (Radix); скорость соло-
  разработки и совместимость с shadcn-экосистемой и артефактами Claude
  Design; prose-слой изолирует контентную типографику от компонентов.
- Минусы / компромиссы: привязка к Tailwind-идиоме (длинные className,
  вкус на любителя); prose требует ручной настройки под русскую типографику;
  дизайн-токены живут в двух проекциях (дизайн-система и theme) - нужен
  порядок синхронизации; конфигуратор рамок может потребовать своих
  стилевых решений (canvas/динамика) - оценить при его проектировании.
- Адаптивность: два брейкпоинта вместо пяти сокращают матрицу тестирования
  (проверять раскладку на всей оси ширины, не только в точках); контейнерные
  запросы делают карточки переносимыми между контекстами без модификаторов;
  компромисс - отход от общеизвестных дефолтов Tailwind (см. альтернативы).
- Дальнейшие шаги: зафиксировать токены в дизайн-системе (Claude Design) и
  спроецировать в `tailwind theme` (цвет и типографика — по решениям пунктов
  1 и 3 дизайн-системы; черновик — в layout-audit.md, п.2.2; секция `screens`
  черновика устарела — брейкпоинты по п. 6 через `@theme`);
  настроить `next/font/local` + положить лицензии PT Sans и PT Sans Narrow
  в репозиторий; добавить линт-запрет arbitrary values; пересмотреть ADR, если
  конфигуратор или магазин упрутся в ограничения подхода.
