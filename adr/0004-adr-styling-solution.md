- Статус: Предложено

- Обновлено: 2026-07-10 — п. 1 и п. 4 приведены к решениям дизайн-системы

- Обновлено: 2026-07-23 — п. 2: Base UI вместо Radix
- Обновлено: 2026-08-05 — п. 1 и п. 4: палитра и шрифт приведены к

## Контекст
Дизайн утвержден и сохраняется (макеты `../graphic_design/Main_iDrp`, разбор в
`../design/graphic/main-idrp-design-audit.md`). Аудит верстки-референса
`legacy/des-2016` (`../audit/layout-audit.md`) дал вердикт «переверстать»:
код стилей непереносим (две параллельные CSS-ветки со 145 дублирующимися
селекторами, float-грид, все размеры в px, классы-краски `.blue`/`.brown`
без семантики - 1041 использование), при этом дизайн-токены извлекаются чисто
(~8 цветовых ролей с дрейфом, 6-8 ступеней шрифта, один радиус 3px).

Ограничения: стек Next.js (App Router) + TypeScript strict (ADR-0002);
журнал мигрирует первым и SEO-критичен (Lighthouse SEO >= 95); статический
путь чтения статьи неприкосновенен (ADR-0003); разработка соло с Claude Code;
дизайн-систему собираем в Claude Design до верстки. Тело статьи приходит как
контентный HTML/MDX из пайплайна - его типографика не может жить в классах
компонентов. Верстки магазина и конфигуратора еще нет - решение должно их
не блокировать, но принимается по данным журнальной вертикали.

## Решение
1. **Tailwind CSS** - основное стилевое решение для всех компонентов.
   Источник значений - **токены дизайн-системы (Claude Design)**, не аудит
   напрямую. По цвету эталон — **брендбук 2014** (решение ревизии
   2026-08-05, Tokens Handoff rev. 4): коричневый `#462512` (Pantone
   4975 C), бирюза `#76c7d1` (630 C), терракота `#d3a086` (7514 C);
   плюс два ранее не задействованных фирменных цвета — `--color-sand`
   `#e0d5bb` (7527 C, тёплые подложки) и `--color-teal-700` `#318ca5`
   (7689 C, тёмные плашки/active); фон страницы белый + карточки `#f1f1f1`
   (вне брендбука, служебный нейтральный). Радиус - единый 3px. Эти токены
   фиксируются в `@theme` и являются единственным источником значений;
   произвольные значения (`text-[#...]`, `p-[13px]`) запрещаются
   линт-правилом. Предыдущий микс «канон аудита верстки 2016 + наши
   значения» (бирюза `#65c6cd`) отменён брендбуком как первоисточником.
2. **shadcn/ui (Radix-примитивы)** - для интерактивных компонентов (меню-
   дровер, оверлей поиска, табы, формы, календарь именин): закрывает
   клавиатурную доступность и фокус-менеджмент, которых в легаси нет.
3. **Типографика статьи** - отдельный prose-слой: `@tailwindcss/typography`
   с конфигурацией под токены (PT Sans, интерлиньяж 1.6-1.7 вместо
   легаси 0.7-1, pull-quote, врезки). Это единственный глобальный
   стилевой контракт с контентом.
4. **Глобальный слой**: Tailwind preflight вместо legacy normalize.css;
   шрифты через `next/font/local` — **три гарнитуры** (решения пунктов 3
   дизайн-системы и ревизии 2026-08-05): **PT Sans** основная (woff2, три
   файла — веса 400/700/italic) + **PT Sans Narrow** для подписей/
   подзаголовков-лейблов (отдельный woff2) + **PT Serif** как резерв
   (веб-замена засечного Century из брендбука; woff2 400/700/italic).
   В `@theme` — три переменные: `--font-sans`, `--font-narrow`,
   `--font-serif`. Тело статьи ПОКА остаётся на `--font-sans` — переход
   prose-слоя на `--font-serif` НЕ выполняется этим ADR, только готовность
   гарнитуры в репозитории. Italic PT Sans — легитимное выделение по
   брендбуку, уже используется в подписях цитат.
   Лицензии всех трёх гарнитур (PT Sans / PT Sans Narrow / PT Serif) —
   в репозитории.
5. Легаси-CSS не переносится ни в каком виде; HTML des-2016 используется
   только как референс структуры блоков, источник истины - макеты.
6. **Адаптивная стратегия и брейкпоинты.** Двухслойная модель:
   viewport-брейкпоинты решают раскладку уровня страницы, контейнерные
   запросы - внутреннюю раскладку компонентов.
   - **Viewport: ровно два брейкпоинта общей раскладки** - `md: 48rem`
     (768px) и `lg: 64rem` (1024px). Они соответствуют якорям макетов
     Main_iDrp (320 / 768 / 1600); диапазоны: до 768 - мобильная
     раскладка, 768-1024 - планшетная, свыше 1024 - десктопная.
     Легаси-дрейф точек (950/951/1223/1224/1280/1281) не переносится.
     Плюс одна **узкоролевая именованная точка** `dock: 100rem` —
     только докинг панели рубрик, в общей раскладке не участвует
     (амендмент 2026-08-09, ниже).
   - **Крупные экраны без брейкпоинта раскладки:** ниже точки `dock`
     десктопный макет обслуживается центрирующим контейнером
     `--page-max: 82.5rem` (1320px, амендмент 2026-08-01) с боковыми
     полями - растет экран, но не контент. От `dock` (100rem/1600)
     центрируется **ансамбль** `--assembly-max: 1650px` (панель 330 +
     контент 1320) — см. амендмент 2026-08-09; контент по-прежнему
     не тянется, сверх 1650 растут поля.
   - **Дефолтные брейкпоинты Tailwind урезаются** до двух выбранных
     (в `@theme`: `--breakpoint-sm/xl/2xl: initial`). Набор становится
     самодокументируемым: каждая точка соответствует макету; агент не
     может повесить `xl:` там, где дизайна не существует. Цена: чужие
     сниппеты с `sm:`/`xl:` молча теряют эффект - принимается осознанно.
   - **Единицы брейкпоинтов - rem** (требование единообразия единиц
     Tailwind v4 + лечение px-болезни легаси: 1381 px-значение, 0 rem).
   - **Компоненты в нескольких контекстах** (карточка материала: крупная /
     оверлей / мини; товарная карточка: сайдбар / ряд / карусель)
     адаптируются контейнерными запросами (`@container`, ядро Tailwind
     v4), а не viewport-точками - одна карточка, ноль классов-модификаторов
     контекста (антириск «классов-красок» из аудита).
   - **Флюидная типографика** (`clamp()`) для заголовков статьи и
     крупных ступеней prose-слоя - вместо промежуточных брейкпоинтов
     (заменяет легаси-прыжки 2em/2.3em/80px).
   - Конфигурация брейкпоинтов - в CSS через `@theme`
     (`--breakpoint-*`), не в JS-конфиге (в Tailwind v4 `screens`
     удален; черновик theme в layout-audit.md п. 2.2 в части `screens`
     устарел и заменяется этим пунктом).
7. **Версия Tailwind: v4 (CSS-first).** Пин: Tailwind CSS v4 (актуальная
   линия 4.3.x на 07.2026). Причина фиксации: обучающие данные генераторов
   кода и большинство туториалов по умолчанию выдают v3-идиому — это
   систематический источник ошибок. Красный флаг: любой сгенерированный
   `tailwind.config.js` с `theme.extend` или директивы
   `@tailwind base/components/utilities` — не v4, откатывать.
   Ключевые расхождения v3 → v4 (используем правую колонку):
   - Конфиг: `tailwind.config.js` → CSS через `@import "tailwindcss"` +
     `@theme { --* }` (JS-конфиг по умолчанию не создаём).
   - Подключение: три `@tailwind`-директивы → одна `@import "tailwindcss"`.
   - Токены: `theme.extend.{colors,fontSize,...}` → CSS-переменные
     `--color-*`, `--text-*`, `--breakpoint-*`, `--radius-*`, `--font-*`
     (включая `--font-sans`, `--font-narrow`, `--font-serif` — см. п. 4).
   - Брейкпоинты: `screens{}` и директива `@screen` удалены →
     `--breakpoint-*` (см. п. 6).
   - Контейнерные запросы: в ядре → плагин
     `@tailwindcss/container-queries` НЕ ставим.
   - Сканирование классов: массив `content[]` не нужен (авто-детект);
     при необходимости — директива `@source`.

## Рассмотренные альтернативы
- **CSS Modules с сохранением существующих классов** - отвергнуто: выгода
  этого пути - реюз готовых стилей, а реюзать нечего (классы не несут
  семантики, общие блоки существуют в двух конфликтующих копиях); получили
  бы ручное сопровождение токенов и перенос дрейфа в новый стек.
- **Чистый CSS + custom properties (без фреймворка)** - жизнеспособно, но
  дисциплина токенов, состояний и адаптивности держится только на
  соглашениях; для соло-разработки с генерацией кода это медленнее и
  дрейфоопаснее, чем энфорс через theme.
- **CSS-in-TS (vanilla-extract и подобные)** - типобезопасность токенов
  привлекательна, но добавляет сборочную сложность, отсекает экосистему
  shadcn/ui и не дает преимуществ для SSG-пути (стили и так статичны).
- **Готовые UI-киты (Bootstrap/Mantine/MUI)** - чужой визуальный язык;
  дизайн уже утвержден и самобытен (дореволюционная орфография, орнаменты),
  переопределение кита дороже сборки из примитивов.
- **Дефолтный набор брейкпоинтов Tailwind (sm/md/lg/xl/2xl)** - отвергнуто:
  640/1280/1536 не соответствуют ни одному макету; лишние точки провоцируют
  «дизайн на глазок» в неспроектированных диапазонах. Совместимость с чужими
  сниппетами ценится ниже самодокументируемости набора.
- **Промежуточный брейкпоинт sm: 480px** - отвергнуто: между 320 и 768
  макетов нет; перестроение сеток карточек в этом диапазоне - задача
  контейнерных запросов на уровне компонента, а не viewport-точки.
- **Брейкпоинт на 1280/1600 под десктопный макет** - отвергнуто: макет 1600
  описывает холст, а не точку перелома; строка на всю ширину 1600 нечитаема.
  Решается max-width-контейнером, не медиа-запросом.
  *Уточнение 2026-08-09:* точка `dock: 100rem` этот вердикт не отменяет —
  она заведена не под «десктопный макет» (общая раскладка по-прежнему
  без точки на 1600), а под единственную роль — докинг панели рубрик;
  контент и на ней ограничен `--page-max`.

## Последствия
- Плюсы: токены навязываются механически (главный антириск аудита - россыпь
  «красок»); a11y-дыры легаси не воспроизводятся (Radix); скорость соло-
  разработки и совместимость с shadcn-экосистемой и артефактами Claude
  Design; prose-слой изолирует контентную типографику от компонентов.
- Минусы / компромиссы: привязка к Tailwind-идиоме (длинные className,
  вкус на любителя); prose требует ручной настройки под русскую типографику;
  дизайн-токены живут в двух проекциях (дизайн-система и theme) - нужен
  порядок синхронизации; конфигуратор рамок может потребовать своих
  стилевых решений (canvas/динамика) - оценить при его проектировании.
- Адаптивность: два брейкпоинта вместо пяти сокращают матрицу тестирования
  (проверять раскладку на всей оси ширины, не только в точках); контейнерные
  запросы делают карточки переносимыми между контекстами без модификаторов;
  компромисс - отход от общеизвестных дефолтов Tailwind (см. альтернативы).
- Дальнейшие шаги: зафиксировать токены в дизайн-системе (Claude Design) и
  спроецировать в `tailwind theme` (цвет — по брендбуку 2014 /
  Tokens Handoff rev. 4; типографика — по решению п. 3 дизайн-системы;
  черновик — в layout-audit.md, п.2.2; секция `screens` черновика
  устарела — брейкпоинты по п. 6 через `@theme`);
  настроить `next/font/local` + положить лицензии PT Sans, PT Sans Narrow
  и PT Serif в репозиторий; добавить линт-запрет arbitrary values;
  пересмотреть ADR, если конфигуратор или магазин упрутся в ограничения
  подхода.

## Амендмент 2026-08-05 — брендбук как эталон цвета и шрифта

Прочитан брендбук 2014 («Руководство по использованию фирменного стиля»,
Pantone-эталоны). Сверка отражена в `Мост к брендбуку.dc.html`
(дизайн-система) и зафиксирована решениями владельца:

1. **Цвет — брендбук эталон, аудит верстки 2016 более не источник.**
   Коричневый `#462512`, бирюза `#76c7d1`, терракота `#d3a086` (терракота
   почти не изменилась — было `#d4a187`, разница 1 единицу RGB, выбор
   пункта 1 дизайн-системы фактически подтверждён). Бирюза меняется
   заметно (`#65c6cd` → `#76c7d1`) — отменяет прежний «микс с каноном
   аудита». Палитра расширена двумя ранее не используемыми фирменными
   цветами: `--color-sand` `#e0d5bb` (Pantone 7527 C) и `--color-teal-700`
   `#318ca5` (Pantone 7689 C).
2. **Шрифт — вводим PT Serif как резерв, не меняем шрифт статьи.**
   Брендбук предписывает Century (засечная) как наборный текст; в вебе
   недоступна. PT Serif принят веб-заменой и должен быть в репозитории
   готовым к использованию, но применение к телу статьи — отдельное
   решение, этим амендментом НЕ принимается (риск для SEO-критичного пути
   ADR-0003 — смена шрифта тела уже мигрированных статей вне рамок
   текущей итерации).
3. **PT Sans Italic — легитимирован**, не только Narrow: брендбук называет
   Italic шрифтом выделения; де-факто уже используется в атрибуциях
   pull-quote — самостоятельного действия не требует, только фиксация.
4. **Логотип**: охранное поле по брендбуку — 2h (двойная высота литер
   названия «Русский Паломник»), не «отступ = высоте знака» из
   предыдущей версии Design Guide. Требование конвертации в вектор
   (п. 5, «Открытые вопросы» — если применимо) не снимается: бренд-бук
   подтверждает допустимые версии лого — коричневая, чёрная, градации
   серого, белая на цветном/тёмном фоне.

Источник данных: `Мост к брендбуку.dc.html`, `Tokens Handoff.md` rev. 4.

## Амендмент 2026-08-09 — точка докинга панели рубрик

Спецификация дизайнеров «Меню и шапка» ввела три режима панели «Журнал»:
`< 1024` — модальный полноэкран с аккордеоном; `1024–1599` — оверлей по
бургеру (в проде немодальный, без подложки); `≥ 1600` — **докинг**: панель
становится постоянной колонкой страницы (бургер скрыт, крестика нет,
интерактива открытия/закрытия не существует — режим обслуживается
серверной раскладкой без клиентского кода). Докинг — смена раскладки
страницы с собственным макетом (`Statiya_menu_1980`), то есть точка
легитимна по критерию п. 6 «каждая точка соответствует макету».

Решения:

1. **Механизм — именованный узкоролевой брейкпоинт**
   `--breakpoint-dock: 100rem` (1600px) в `@theme`. Роль единственная:
   докинг панели рубрик; для смены общей раскладки и любых иных нужд
   точка не используется. Отвергнуты: воскрешение `2xl` (общепринятое
   значение 96rem — имя лгало бы, систематический источник ошибок
   генераторов, ср. п. 7) и голый `@media (width >= 100rem)` вне темы
   (магическое число, невидимое утилитами и линтом).
2. **Токены геометрии:** `--panel-w: 330px`, `--assembly-max: 1650px`
   (330 панель + 1320 контент). Выше `dock` центрируется ансамбль
   `--assembly-max`; сверх 1650 растут поля, контент не тянется.
   Тезис «выше lg брейкпоинтов нет; макет обслуживается `--page-max`»
   уточнён по месту (п. 6): верен ниже `dock`.
3. **Коридор 1600–1649:** ансамблю не хватает до 1650 — контентная
   коробка ужимается (до ~1270). Принято осознанно (решение владельца);
   альтернатива «докать с 1650» отклонена.
4. **Механика раскладки** — грид-ансамбль
   `[var(--panel-w) minmax(0, var(--page-max))]` с
   `max-width: var(--assembly-max)` и центрированием; ансамбль — сосед
   шапки (панель структурно подчинена глобальной навигации), панель в
   потоке и уходит со скроллом. Приёмы прототипа `Статья.dc.html`
   (`margin-left: -330px` + компенсация ширины шапки,
   `position: absolute` от вычисленной высоты шапки,
   `getBoundingClientRect`) не переносятся: замер раскладки JS-ом и
   парные взаимо-гасящие сдвиги — симптомы панели вне потока; в потоке
   они не нужны.

Синхронизация: в Tokens Handoff (готовый блок `@theme`, п. 6 хендоффа)
добавить `--breakpoint-dock`, `--panel-w`, `--assembly-max` и снять
формулировку «выше lg брейкпоинтов нет»; лист состояний — дополнить
режимом «панель-колонка» (правки на стороне дизайн-системы).
