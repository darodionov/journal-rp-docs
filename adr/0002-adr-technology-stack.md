# ADR-0002: Технологический стек

- Статус: Принято
- Дата: 2026-07-08 (решение принято 2026-07-01, оформлено задним числом;
  на этот ADR уже ссылаются ADR-0005 и ADR-0006)

## Контекст
Legacy-сайт (PHP 7 / Silex, местами Vue/jQuery, MySQL без PDO, запросы в коде)
переписывается с нуля. Сайт — три продукта с разными профилями рендеринга:
журнал (контент, SEO-критичен), магазин (каталог + транзакции), конфигуратор
рамок (клиентский SPA-остров). Разработка соло с помощью агентов (Claude Code).

Двойная цель проекта: рабочий продукт, который «не стыдно показать», + прокачка
систем-дизайна и глубокое освоение востребованного стека (учебная цель владельца:
TypeScript, React, Next.js). Критерии выбора: рыночный сигнал, пригодность для
соло-разработки с агентами, покрытие всех трёх профилей рендеринга одним стеком.

Инвариантный костяк архитектуры зафиксирован до выбора фреймворка и от него не
зависит: статический путь чтения через CDN + инкрементальная регенерация +
аккуратные динамические края + отдельный слой поиска + SEO/редирект-инфраструктура.

## Решение
Единый стек на весь проект:

- **Next.js (App Router)** + **TypeScript strict** — все три вертикали. Не Pages
  Router: актуален и учит только App Router (RSC, Metadata API, ISR).
- **Рендеринг журнала:** SSG + ISR; статический путь чтения раздаётся с CDN
  (детализация — ADR-0005).
- **Контент на старте:** MDX в репозитории + валидация фронтматтера через Zod —
  типизированный контент; эволюция авторинга — ADR-0003.
- **Дизайн-система:** Tailwind CSS + shadcn/ui — общая для журнала и будущего
  магазина (детализация и prose-слой — ADR-0004).
- **Данные:** Postgres + Drizzle — только для динамических краёв, НЕ на пути
  чтения статьи. Zod на всех границах; типизированные запросы; без сырого SQL.
- **Коммерция (будущая вертикаль магазина):** не писать свой движок корзины/
  чекаута — headless-бэкенд (ориентир Medusa) либо тонкая логика + платёжный
  провайдер; выбор — отдельным ADR при старте вертикали.

## Рассмотренные альтернативы
- **Astro для журнала + Next для магазина** («правильный инструмент под профиль
  нагрузки») — для чисто контентной вертикали Astro легче и точнее (ноль JS по
  умолчанию, Content Collections). Отвергнуто владельцем в пользу унификации:
  одна ментальная модель, один пайплайн, максимальная поддержка агентами, и
  Next.js сам по себе — учебная цель. Осознанная жертва оптимальностью вертикали
  ради простоты единого стека.
- **Kotlin/Spring API + тонкий TS-фронт** — сильный enterprise-сигнал бэкенда,
  но два стека на одного разработчика и слабее совпадение с целью «выучить
  React/Next»; SSR-вопросы фронта пришлось бы решать отдельно.
- **Рефакторинг легаси на месте** (PDO/слой данных без переписывания) — дешевле
  для бизнеса, но не достигает учебной цели и цели портфолио; отвергнуто с
  открытыми глазами: rewrite выбран не по бизнес-нужде, а ради обучения, при
  митигировании рисков через strangler-fig.

## Последствия
- Плюсы: один фреймворк и один язык на все вертикали; ISR закрывает ось «масштаб
  изменения + свежесть»; типы + Zod + агенты — рабочая связка для соло; стек с
  максимальным рыночным сигналом совпадает с учебной целью.
- Минусы / компромиссы: для чистого контента Next тяжелее необходимого — за
  лёгкость страниц надо бороться (RSC по умолчанию, острова-листья — ADR-0004/0005);
  завязка на эволюцию App Router (два поколения кэш-API — риск смены сигнатур);
  Payload/Medusa как будущие спутники стека — отдельные решения своих фаз.
- Дальнейшие шаги: закрыты последующими ADR (0003 — контент, 0004 — стили,
  0005 — сборка/кэш, 0006 — URL/редиректы) и учебным планом
  (learning-build-plan.md).
