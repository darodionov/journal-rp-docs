# ADR-0003: Архитектура контента — авторинг, хранение, доставка

- Статус: Принято
- Дата: 2026-07-03

## Контекст
Журнал стартует с контентом как MDX-в-репозитории (см. ADR-0002). Это неявно требует
git-грамотных авторов. Вероятное развитие: контент создают и редактируют журналисты и
редакторы — не-технические. Это триггер пересмотра, помеченный в брифе.

Отдельно: семантический поиск/RAG требует не document-базы, а векторного хранилища;
pgvector в уже имеющемся Postgres — путь наименьшего трения (прошлый анализ).

Нужно решение, которое: (а) не строит CMS вперёд нужды; (б) сохраняет обратимость;
(в) не ломает статический путь чтения и SEO; (г) не смешивает три ортогональных
хранилища — каноническое хранилище контента, полнотекстовый индекс, векторный индекс.

## Решение
Развязать авторинг и доставку и зафиксировать принцип, а не продукт.

1. Ввести абстракцию источника контента (ports & adapters) сразу при реализации чтения
   статей: путь чтения потребляет контент через тонкий интерфейс
   (`getArticle`, `listArticles`, `getArticleSlugs`), а НЕ импортирует MDX напрямую.
   Конкретный бэкенд — сменный адаптер за этим швом.
2. Пока авторы технические — адаптер = MDX-в-репозитории (per ADR-0002).
3. При появлении не-технических авторов каноническое хранилище переезжает в headless-CMS
   сменой адаптера (локальное изменение, не переписывание). Доставка остаётся статической:
   публикация → webhook → `revalidateTag` → пересборка страницы → CDN; предпросмотр для
   редакторов — через draft mode.
4. Три хранилища остаются раздельными: каноническое (MDX → CMS), полнотекстовый индекс
   (внешний сервис vs Postgres FTS — открыто), векторный (pgvector в том же Postgres).
5. Выбор конкретного CMS-продукта отложен до срабатывания триггера. Направление:
   pgvector-в-том-же-Postgres и связность со стеком (Next + Postgres + Drizzle) склоняют
   к Payload (self-host, TS-native, Postgres через Drizzle); Sanity — альтернатива, если
   приоритет — редакторский опыт и real-time при нежелании держать инфраструктуру.
   Полный разбор кандидатов — в `../design/cms-options.md`.

## Рассмотренные альтернативы
- Оставить MDX-в-репозитории навсегда и требовать git от журналистов — отвергнуто:
  не-технические авторы этого не потянут; неверный инструмент под редакционный процесс.
- Заранее перенести контент в document-NoSQL «под RAG» — отвергнуто: RAG требует векторного
  хранилища, а не document-DB; NoSQL для RAG в лучшем случае паритет с Postgres+pgvector, при
  этом уводит контент из уже имеющегося Postgres. Спекулятивная общность.
- Выбрать CMS-продукт сейчас — отвергнуто: строит вперёд нужды и замораживает решение до
  появления реальных требований (размер команды, процесс, редактор, медиа).
- Делать server-rendered каждую страницу при переходе на CMS — отвергнуто: ломает статический
  путь чтения и SEO без нужды; headless + ISR сохраняет оба.

## Последствия
- Плюсы: переход на CMS — локальная замена адаптера, а не переписывание; статический путь
  чтения и SEO сохраняются; хранилища не смешиваются; RAG-будущее (pgvector) не замкнуто;
  решение обратимо (можно уйти в CMS, позже — в выделенную векторную БД, если масштаб потребует).
- Минусы / компромиссы: абстракция источника контента — небольшая доп. работа и один слой
  косвенности сейчас, до того как он «понадобится»; но ретрофит дороже. Переход на CMS приносит
  новые заботы (расписание при статике, медиа-пайплайн, роли/процесс, предпросмотр) — каждая
  проектируется отдельно. Self-host CMS (если Payload) добавит операционную нагрузку (бэкапы,
  миграции схемы, возможные холодные старты админки на serverless).
- Дальнейшие шаги: реализовать абстракцию источника контента в первой вертикали чтения; при
  срабатывании триггера — отдельный ADR с выбором конкретного CMS-продукта (заместит пункт
  «продукт отложен» здесь); ADR по стратегии полнотекстового поиска и ADR/срез по pgvector —
  когда возьмёмся за поиск.
